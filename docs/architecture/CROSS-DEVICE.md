## 1. 产品判断

跨设备操作是真实需求，也是当前人工验收过程中暴露出的主要门槛：

- 用户不知道另一台设备的 IP、用户名或 SSH 配置
- Windows、Linux、macOS 的登录方式不同
- 公钥、权限和防火墙配置对普通用户过于复杂
- Agent 无法仅凭“同一 Wi-Fi”自动获得安全访问

这个需求值得加入 Skill，但产品形式不能是“让用户配置 SSH，然后允许 Agent 执行任意 shell”。

正确形式是：

```text
控制设备上的 Agent
    ↓ 一次性配对
目标设备上的 archielink 伴侣进程
    ↓ 仅允许语义化 RPC
远程诊断 / 计划 / 后续受控操作
```

## 2. 首期范围

首个版本只交付同局域网内的只读跨设备体检：

- 主设备发现目标设备的一次性配对入口
- 用户在目标设备确认会话
- 读取目标设备的 `detect`、`plan`、`doctor`
- 将结构化结果传回主设备
- 会话结束自动关闭端口和清理临时密钥

首期不做：

- 任意远程 shell
- 远程文件浏览
- 无人值守常驻
- 跨公网中继
- 自动安装系统组件
- 远程修改 DNS、路由、代理或 VPN

## 3. 用户场景

### 3.1 家庭多设备

用户在主电脑上让 Agent 检查同一 Wi-Fi 下的 Windows 电脑、Linux 服务器或电视，不需要自己配置 SSH。

### 3.2 远程协助

技术支持人员让用户在其设备上打开一次性会话码，控制端运行只读诊断，不获取永久登录权限。

### 3.3 后续受控设置

当目标平台的支持级别为 `auto`，且本地自动模式已经稳定后，才允许在双端明确确认下执行受控设置和回滚。

## 4. 角色

| 角色 | 职责 |
|---|---|
| Controller | Agent 运行的主设备，发起配对和诊断 |
| Target | 被检查的设备，运行 `archielink` 伴侣进程 |
| Pairing Code | 短时、一次性的配对材料 |
| Session | 单次连接、单次授权和有限 RPC 集合 |

## 5. 配对流程

1. 用户在目标设备运行：

```bash
archielink remote serve --once
```

2. 目标设备显示：

- 局域网端点
- 二维码
- 短配对码
- 会话过期时间
- 目标设备平台摘要

3. 控制端 Agent 调用：

```bash
archielink remote connect <pairing-code> --json
```

4. 目标设备显示连接来源，并要求用户确认。

5. 双方完成会话密钥确认后，才允许调用白名单 RPC。

6. 诊断结束后，目标设备自动关闭监听并清理临时材料。

## 6. 允许的远程接口

首期只允许：

```text
hello
capabilities
detect
plan
doctor
close
```

禁止：

- `shell`
- `exec`
- `read_file`
- `write_file`
- `download_url`
- `install`

后续受控设置阶段只能新增明确命名的能力，例如：

```text
setup.prepare
setup.apply
setup.verify
setup.rollback
```

每个能力都必须有独立授权和本地确认。

## 7. 身份与授权

- 不要求用户提供 Windows/Linux/macOS 登录密码。
- 不使用永久 SSH 私钥。
- 配对材料只能单次使用并在短时间后过期。
- Controller 和 Target 都必须显示并确认设备身份。
- 会话密钥只保存在内存或临时文件中，权限为最短生命周期。
- 连接来源、平台和目标身份必须写入脱敏日志。
- 任何证书或指纹不匹配都立即终止。

## 8. 安全不变量

1. 默认关闭，只有用户主动启动目标会话。
2. 一次配对只能建立一个会话。
3. 配对码过期、被拒绝、重复使用或指纹不一致时失败关闭。
4. 远端 helper 不接受任意命令字符串。
5. 远程 RPC 只能返回结构化 JSON。
6. 不读取 `.env`、Cookie、支付凭证、私钥和系统登录信息。
7. 会话结束后不得留下监听端口、临时密钥或授权文件。
8. 同一目标设备同时只允许一个远程会话。
9. 不以“同一 Wi-Fi”作为身份认证。
10. 默认只扫描本地网段或使用明确的端点，不做无边界公网发现。

## 9. 传输方案

首期优先采用同局域网直接连接，使用临时相互认证和 TLS 通道。

不把 SSH 作为普通用户默认方案：

- Windows OpenSSH 安装和 ACL 配置门槛高
- 用户可能没有密码
- 管理员授权文件容易配置错误

SSH 可以作为开发者高级传输模式，但必须复用相同的会话授权和 RPC 白名单，不能变成任意 shell。

跨公网中继不属于 V0.9，需要单独的隐私、带宽、滥用和成本设计。

## 10. 平台降级

| 目标平台 | 首期行为 |
|---|---|
| macOS | 运行只读 helper |
| Windows | 运行只读 helper，无需永久 SSH |
| Linux | 运行只读 helper |
| Android / iOS | `guided`，只传配对和配置摘要 |
| HarmonyOS 手机 / 智慧屏 / PC | 由伴侣 HAP 提供语义化接口 |
| 电视 | 由电视伴侣应用显示会话码 |
| 云沙箱 / 容器 | `unsupported` |

## 11. 失败与清理

必须覆盖：

- 控制端取消
- 目标端拒绝
- 配对码过期
- 网络中断
- 平台命令失败
- helper 崩溃
- 会话超时

每种失败都必须：

- 关闭监听
- 删除临时密钥
- 返回稳定错误码
- 保留脱敏诊断

## 12. 商业价值

跨设备协作可以成为独立付费能力：

- 家庭多设备诊断
- Windows 和 Linux 设备辅助
- 电视和鸿蒙设备接入
- 远程售后支持
- 多设备统一授权

它不能作为“任意远程控制”出售。产品文案必须强调只读诊断、单次配对和用户确认。

## 13. 验收

1. macOS 控制端可以完成 Windows 目标设备的只读诊断，不需要用户配置 SSH。
2. macOS、Windows、Linux 之间至少完成双向配对。
3. 配对码过期、错误、重复使用时失败关闭。
4. 未确认的目标设备不能执行 RPC。
5. 未列入白名单的方法返回拒绝错误。
6. 会话结束后目标端没有监听端口、临时密钥和授权文件。
7. helper 崩溃后控制端在时限内收到失败。
8. Windows 和 Linux 的 JSON schema 与本地 doctor 一致。
9. 不读取任何秘密文件或系统登录信息。
10. 日志中不出现完整配对码、私钥和控制端账户凭据。

## 14. 版本安排

### V0.9：跨设备只读协作

- 同局域网一次性配对
- Controller / Target CLI
- 只读 RPC
- 自动清理
- macOS、Windows、Linux

### V1.0 后：跨设备受控设置

只有在本地自动设置稳定、平台完成授权并且用户双端确认后，才增加：

- 远程 setup
- 远程 rollback
- 远程状态订阅
- 多设备任务

远程写操作不进入 V0.9。

## 15. Developer-Assisted Device Bridge

跨设备开发者辅助是 V0.9 之后的独立 D-track，不属于只读协作：

- Host 可以通过官方 ADB/HDC 安装和启动已签名伴侣应用；iOS 走零伴侣轨道（官方 WireGuard App 配置导入），Host 不操作 iOS 设备。
- 安装和启动不能让 Host 获得任意 shell 或文件系统权限。
- 系统 VPN 授权必须由目标设备用户完成。
- Host 与伴侣应用只能调用 `hello`、`capabilities`、`prepare`、`start`、`status`、`stop`、`close`。
- 配对、设备身份确认、会话过期、自动清理和调试模式风险提示是必需项。
- 不适用隐藏工厂码、自动点击授权、持久开放 ADB/HDC 或云端任意控制。

目标用户必须具有基本动手能力并信任 AI 工具；独自无法完成时，可以使用远程语音、屏幕指导或经过双端确认的语义化辅助。

完整方案见 [Host-Assisted Device Bridge 计划](../plans/2026-11-07-archie-link-host-assisted-device-bridge.md)。
